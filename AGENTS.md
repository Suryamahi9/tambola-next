# Tambola Next

Online Tambola/Housie app: landing page, live voice caller (`/game`), ticket generator (`/tickets`), rules (`/rules`), and paid multiplayer party rooms (`/play` → `/room/[id]`, player history at `/history`). Every page is public — `/game` and `/tickets` need no login; `/play`, `/room/[id]`, `/history` are gated by the `tambola_player` cookie (player persona, minted at checkout). Origin: `https://github.com/Suryamahi9/tambola-next.git` (branch `main`).

## Commands

- `npm run lint` — eslint; must be clean (errors block work).
- `npm run build` — `next build` (Turbopack); this is also the typecheck.
- `npm run dev` / `npm run start` — dev / prod server.
- No test runner is configured. Verify changes by lint + build + the headless harness (see below).

## Stack

- Next 16.3.0 (breaking changes — see block above), React 19, TypeScript, Tailwind v4 (`@import "tailwindcss"` + `@theme inline` in `app/globals.css`).
- `lib/ticket.ts` — pure ticket engine, no deps: `generateTicket` (may return null after 300 tries — callers must guard), `generateUniqueGrids` (may return short), `generateStrip`, `generateSetTickets` (fresh strip per call — cross-player uniqueness comes from the room's shared-book cursor, not here), `generateSetBatch`/`generateHalfSetBatch` (validated at maxRun 4), `isValidTicket(grid, maxRun=3)` (solo random tickets reject 3-in-a-row runs; the showcase validates at 4 so set tickets never false-flag), `gridKey`, `loadBatches`/`saveBatch` (localStorage, currently unused). `lib/site.ts` — site config/metadata + nav/audio/voice lists.
- `stitch_tambola_party_live_caller/` = committed design mockups (screenshots + standalone `code.html`). Reference only — nothing in `app/`/`components/` imports it; don't wire it into the build.

## Design constraints (dark-only glassmorphism)

- `<html>` carries a permanent `dark` class; body is `bg-[#080808]` (obsidian black) with a `.grain` film overlay. No ThemeToggle and no light mode — do not add theme switching. Identity = **Black & Gold luxury**: obsidian `#080808` canvas, midnight `#111111` surfaces, metallic gold `#D4AF37` primary, champagne `#F7E7A1` highlights, antique gold `#8C6A18` borders/shadows, warm ivory `#FFF9E8` text, emerald `#087A52` for success/win. Gold must read as polished metal (layered gradients/highlights/reflections), never flat yellow. Permanent dark identity only.
- Token names in `@theme inline` (`globals.css`) are frozen — only values change. Signature utilities: `.gold-text` (foil headline gradient), `.gold-face` (metallic-gold button face, dark-ink text), `.gold-sheen`/`.gold-glow`/`.gold-ring`/`.gold-rule`/`.gold-border` (gold accents), `.marble` (subtle stone texture), `.glass`/`.glass-subtle`/`.glass-high` (translucent cards), `.marquee-bulbs` (bulb-strip divider, aria-hidden), `.stub-divider` (dashed divider), `.ornate-border`/`.paisley-pattern` (retuned gold ornaments), `.carnival-glow` (gold), `.canvas-vignette`, `.reveal`/`.reveal.is-visible` (scroll reveal), `.cursor-glow`. Prefer these over new arbitrary colours.
- Two design dialects coexist — match the one the file you're editing already uses:
  - Room / caller / history UI uses Material-3-style tokens defined in `@theme inline` in `globals.css`: `bg-surface-container{,-low,-high}`, `text-on-surface[-variant]`, `text-primary/-secondary/-tertiary` (and -container/-fixed variants), and paired `font-{display-hero|headline-*|body-*|label-*}` + `text-{same-scale}` classes. Room components freely use `backdrop-blur-xl`/`2xl`.
  - Older/other pages use the `.glass` / `.glass-subtle` / `.glass-high` classes (`globals.css`) — translucent fill + `backdrop-filter` blur + inset highlight — plus `border-primary/20` and hex tones like `text-on-surface-variant`. Don't build solid `bg-white ... dark:bg-neutral-900` cards.
- Tickets render through `components/tickets/TicketCard.tsx`, which separates a **theme** (colour palette) from a **design** (structural layout):
  - Themes: 29 `TicketTheme`s in `THEMES` — 26 curated + `print`/`dots` B&W print-shop + `custom`; default `paperwhite`. Designs: 10 `TicketDesign`s — classic/carnival/stub/metro/aura/blueprint/royal/neon/postage/boarding (`DESIGN_ORDER` in the generator appends new ones at the end so "all mixed" rotation of the old six is unchanged; neon owns its dark shell + white numbers like Carnival owns its palette).
  - Props: `style` (theme), `design`, `customTheme?: ThemeSpec` (static class shell used when `style === "custom"`), `customStyles?: CustomStyles` (live colours as inline styles), `called?: ReadonlySet<number>` (highlights drawn numbers). Exports `THEME_LABELS`/`DESIGN_LABELS`, `STYLE_LABELS` (theme-alias of `THEME_LABELS`), and `ThemeSpec`.
  - A "NAVEEN CHERRY" watermark is painted on every design via the theme's `watermark` colour. Watermark text is uppercased at render (`Watermark` + PDF), and the panel colour input overrides its colour via the `watermarkColor` prop ("" = theme default). `#TKT-XXXXXX` serials were removed from cards on request — cards show only position (`No. 03 / 12`); don't reintroduce hash serials (the `serial`/`serialMuted` ThemeSpec fields are label colours, not the removed feature).
  - Uploaded logos render as a centred ghost (grayscale + slight blur; width = % of ticket width, height = max-height % of ticket height) so numbers stay legible — do NOT regress to full-bleed `inset-0` sizing or a fixed height cap (starves square/portrait logos, slider looks dead). The Logo fit toggle (`logoFit` prop: `fit` = whole logo via contain, `fill` = exact box via cover/crop) exists because contain binds to the limiting axis, making one slider feel dead on mismatched logo shapes. Same ghost rules in the PDF export (`downloadPDF` always uses fit — cropping on paper is worse than letterboxing). Width (15–100%) + height (15–100%) + logo/watermark depth sliders feed `logoWidth`/`logoHeight`/`logoOpacity`/`watermarkOpacity` props (fractions) and persist in `tambola-generator-prefs` (legacy `logoSize` migrates to both); watermark 0% hides the background text (header name stays).
  - Generator: Ticket zoom slider (70–130%, default 100, persisted as `ticketZoom`; legacy Compact/Standard/Large prefs migrate to 90/100/105). Zoom drives both the container `zoom` and the sm+ deck density (≤92% → 3–4 cols, ≥103% → 1–2 cols, else 2–3 cols). The showcase grid is single-column on phones (`grid-cols-1 gap-2`, `sm:gap-4`) — base MUST stay an explicit `grid-cols-1`, never bare `grid`: an implicit auto track sizes to max-content, so a long watermark stretches tickets past the phone frame and the browser zooms out. The Custom Theme Editor builds live hexes into `customStyles` (inline styles — runtime Tailwind classes are never generated, so dynamic `from-[${hex}]`-style classnames silently break) + a static class shell, persisted in `tambola-generator-prefs` (corrupt JSON keeps defaults, never disables saving). Fill Names labels round-robin; toasts report actual counts. Print hides the customizer (`no-print`); PDF yields every 10 pages and refuses past 200 tickets; logo uploads cap at 800KB.
  - Room view and win popup render through `TicketCard` with the default theme + classic design + `called`.
  - The 3D scene is NOT TicketCard-driven: `TambolaScene.tsx` paints its own canvas textures (cream carnival-paper look), so a TicketCard restyle needs no scene work.

## 3D scene gotchas (hard-won)

- Scene = `components/landing/TambolaScene.tsx` (R3F Canvas) + `TambolaSceneLoader.tsx` (Client Component wrapper using `next/dynamic` with `ssr: false`). In Next 16, `ssr: false` is only allowed inside a Client Component, hence the loader.
- Only `three` + `@react-three/fiber` are installed. **`@react-three/drei` is deliberately absent** — it caused a dev-only Turbopack `_instanceof` ReferenceError that killed the 3D render. Do not reinstall it.
- Camera framing (`layoutParams`: fov/backZ/xSpread) is responsive to viewport aspect so the ticket album fits portrait phones.
- The scene mutates the camera inside `useFrame`. ESLint's `react-hooks/immutability` rule flags this (false positive) — needs an eslint-disable on both the `useFrame` call line and the `camera.fov` assignment line.

## Sessions & storage

- **One auth system: the player persona.** `/game` and `/tickets` are public (no gating, no `force-dynamic` — they can be static). The `tambola_player` persona cookie (role `player`) gates `/play`, `/room/[id]`, `/history`. There is no member/account system.
- `lib/auth/session.ts` — HMAC-SHA256 signed `uid.role.exp` tokens (`signToken`/`verifyToken`) + `secureCookieFlag()` (Secure on Vercel, `COOKIE_SECURE` override). `PLAYER_TOKEN_DAYS=30` (players).
- `lib/auth/secret.ts` — `getSessionSecret()`: prefers `AUTH_SECRET`; otherwise generates + persists the secret once (Blob `tambola/secret.txt` when `BLOB_READ_WRITE_TOKEN` is set, else the gitignored `data/secret`). A read-only FS with no Blob — or an unreachable/suspended Blob — falls back to an ephemeral in-memory secret so requests never 500 (set `AUTH_SECRET` to make it stable).
- **Storage is dual-backend.** With `BLOB_READ_WRITE_TOKEN` set, the session secret + party rooms live in Vercel Blob (`@vercel/blob` SDK, private store, `useCache:false`, `allowOverwrite:true`). Without it they fall back to the gitignored local `data/` directory (dev). Do NOT write to the filesystem in prod — Vercel's FS is read-only.
- `lib/store-error.ts` `describeStoreError()` classifies store/Blob failures (suspended store, bad/expired token, 403, rate limit, network, read-only FS) so each reports its real cause. Used by `app/api/rooms/[id]/respond.ts` `roomFailure()`.
- Every cookie-reading page/route (`/play`, `/room/[id]`, `/history`, all `/api/rooms/*` + `/api/payments/*`) must `export const dynamic = "force-dynamic"` — omitting it stale-caches room/player state.
- Copy `.env.example` → `.env.local`.

## Party Rooms (multiplayer)

- Flow: `/play` (name + ticket count + optional room-code join) → Razorpay checkout (or test-mode auto-approve) → `/room/[id]` lobby → the **host starts** once **15 paid tickets** are in. "Host" = `players[0]` while paid, else any paid player (`isEffectiveHost` — an abandoned unpaid first slot can't strand a paid room). Rooms hold **15–50 tickets** counting unpaid reservations too; one player may buy **1–5 tickets** (`MAX_TICKETS_PER_PLAYER`). The room **auto-starts only when it fills to 50** (`MAX_ROOM_TICKETS`) — otherwise it waits for the host. Host start is `POST /api/rooms/[id]/start`. Player tokens/cookies live 30 days (`PLAYER_TOKEN_DAYS`).
- **No WebSockets.** Next 16 has no socket support and Vercel serverless can't hold connections. Rooms sync by **2s polling** from `components/room/RoomView.tsx` (`GET /api/rooms/[id]`, `cache: "no-store"`); the caller auto-draws every 5s by default (adjustable in `CallerControls`: 2/3/5/10/15/30s). Do NOT scaffold a socket server.
- Room code lives in `lib/room/`: `types.ts` (`Room`, `Player`, `PublicRoom`, `Win`, `PendingOrder`), `store.ts` (dual-backend `data/rooms.json` + Blob `tambola/rooms.json`, in-memory cache, per-room write queue via `withRoom()` — which persists the FULL freshly-loaded list, never the cache subset), `engine.ts` (create/join/start/host-gated start/call/claimBingo/nextRound/takeover, `TICKETS_TO_START=15` minimum, `MAX_ROOM_TICKETS=50` cap, price via `ROOM_TICKET_PRICE` default ₹20), `wins.ts` (pure pattern detection + prize awarding + `patternRank` for lineOrder-aware priority).
- **Winning:** after every draw, `callNumber` runs `awardPrizes` (in `lib/room/wins.ts`) which auto-awards **one prize per pattern** — priority Full House → Corners → lines per host `lineOrder` → Early Five — to the first paid player (join order) whose ticket completes it. The game keeps running until **Full House** is won or all 90 numbers are called; an earlier line win does NOT end the game. Players can also press "Bingo!" → `POST /api/rooms/[id]/claim` (`claimBingo` validates the ticket server-side, awards the highest-priority unclaimed pattern per the same ranking, first valid claim wins). `room.winner` only ever upgrades to a higher-priority pattern, never downgrades. **Multi-round:** `POST /api/rooms/[id]/round` (`nextRound`, host-only) deals fresh tickets to paid players, bumps `room.round`, clears `finishedAt`, sets caller to the starter, adds 1 point to `standings` per prize, and keeps a `history` of the last 20 rounds (each entry stores ALL its prizes with player ids). Everyone sees a win popup (winning ticket + all prizes + all players) in `RoomView`; a room with no winner ends naturally at 90 numbers.
- **Host-configurable prizes:** `Room.settings` (`lib/room/types.ts`) holds which of the 6 patterns are active + `lineOrder` (priority of top/middle/bottom). Edited pre-start from `components/room/RoomSettingsEditor.tsx` → `POST /api/rooms/[id]/settings` → `updateRoomSettings` (effective-host-only; route rejects duplicate `lineOrder` entries and empty patches with 400).
- **`withRoom` always reloads the room fresh from the backend** before mutating (not from the in-memory cache) so concurrent serverless instances don't clobber each other; reads via `getRoomById` may use the cache.
- Player identity = HMAC-signed `tambola_player` cookie (reuses `lib/auth/session.ts` `signToken`/`verifyToken` with role `player`), set by `POST /api/payments/create`. No signup. Tickets are dealt from a **shared 90-number book**: the room keeps a strip cursor (`dealStrip`/`dealOffset` on `Room`, see `dealFromRoom` in `engine.ts`), so consecutive players consume tickets from the same `generateStrip()` book and numbers never repeat **across players** within it. The engine rolls to a fresh book when the current one can't fit a player's count, and a player's set always comes from one book so it stays unique — if two devices appear to share a ticket, they're the same cookie/player in the same browser.
- Payments: Razorpay orders via `POST /api/payments/create` (records the order on the room via `recordPendingOrder`) + signature-verified `POST /api/payments/verify` (`consumePendingOrder` enforces order freshness, player match, exact amount, single use). **Without `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` the flow runs in test mode** and verify auto-approves — keep that working when exercising the room locally. `markPaid` is waiting-only and idempotent (re-verify never double-announces).
- The server draws numbers (`callNumber` picks at random from uncalled) so the board can't be tampered with; only `room.callerId` can call. `POST /api/rooms/[id]/caller` hands over only to paid players and refuses to wrest a live game from an active paid caller. A malformed manual pick is a 400, never a silent random draw.
- **Room chat rides the same 2s poll** — messages live on the room object (`Room.messages`, capped at `MAX_CHAT_MESSAGES=100`, oldest dropped) so no extra sync layer. Send = `POST /api/rooms/[id]/message` (`sendMessage` in `engine.ts`): player cookie required, string-only, 240-char cap, 1.5s per-player rate limit (429). Game events (start, milestones every 10 draws, prizes, claims, rounds, caller takeover) auto-post system lines via `postSystemMessage`. UI = `components/room/ChatPanel.tsx` (auto-scroll + unread badge; seen-state advances in an effect, not render). Chat constants live in `lib/room/types.ts` (client-safe) — do NOT import `engine.ts` or `ai.ts` from client components, they pull in `node:crypto`.
- **AI announcer** = `lib/room/ai.ts`. Chat lines starting with `@bot` or `/help /rules /patterns /prizes /status` are answered by the bot (posted as `kind:"ai"` AFTER the user message; the bot section is try/catch-guarded so it can never fail the send). With `OPENAI_API_KEY` (or any OpenAI-compatible `AI_BASE_URL` + `AI_MODEL`) it calls `/chat/completions` via plain fetch; without keys it falls back to canned replies so chat still works end-to-end locally.
- `GET /api/rooms/[id]` returns `{ room, me, myTickets }` — a player only ever sees their own grids. All room route handlers use `params: Promise` (must `await`) and `export const dynamic = "force-dynamic"`. Engine errors carry HTTP statuses (404/403/429/400/422 mirrored by routes via `respond.ts`, default 409); every handler try/catches to JSON 500s so Blob blips never surface as unhandled rejections. `/room/[id]` redirects cookieless visitors to `/play` server-side.
- **Player history at `/history`**: `app/history/page.tsx` (player-cookie-gated, `force-dynamic`) aggregates every room a `tambola_player` was in via `lib/room/history.ts` `playerGameHistory()` scanning `getAllRooms()`; every prize counts once (current-round `room.prizes` + all stored round summaries, matched by player id with name fallback), calls are lifetime-summed. This is a full read of the rooms store — no per-player store exists.
- Next 16 gotcha: **do not set cookies via `NextResponse.cookies.set` in route handlers — the `Set-Cookie` header is silently dropped.** Use `(await cookies()).set(...)` from `next/headers` instead.
